# 密语 SecureChat：简历项目说明与面试准备

## 项目定位

项目名称：基于 SM2 / SM3 / SM4 的桌面安全通信系统。

项目性质：密码学课程实验与个人技术展示项目。

项目地址：https://github.com/zyx0638/securechat-sm2-sm4

技术栈：Python 3.12、Tkinter、TCP Socket、cryptography、gmssl、Pillow、unittest。

这个项目可以展示密码库应用、身份认证与密钥协商、TCP 协议处理、文件流式传输、桌面事件处理及安全负例测试能力。应按照实际个人贡献、已掌握内容和真实时间填写简历，不要将整个仓库功能自动视为个人独立完成的成果。

**基于 SM2 / SM3 / SM4 的桌面安全通信系统 | Python、TCP、Tkinter**

## 建议掌握的面试问题

1. **为什么同时使用非对称与对称算法？** SM2 用于身份签名及小数据随机挑战，X25519 协商共享秘密，SM4 承担消息和文件的数据加密，避免直接用非对称算法加密大文件。
2. **签名为什么仍需要人工核验指纹？** 自签的握手能证明发送者持有对应私钥，但首次连接时，公钥属于谁仍需通过可信渠道确认。保存指纹后才可识别后续身份变化。
3. **为什么 CBC 还需要 HMAC？** CBC 本身不保证完整性。先验证覆盖会话、序号、IV 和密文的 MAC，再解密，可拒绝被修改的记录，避免先处理不可信密文。
4. **如何区分重放与正常的新消息？** 每个方向分别维护严格递增的序号；旧记录、乱序记录以及其他会话记录无法通过对应检查。
5. **为什么密钥分方向？** Alice 到 Bob 与 Bob 到 Alice 使用独立密钥材料，两个方向的序号和认证也分别处理，减少方向混淆。
6. **为什么不直接以口令加密聊天？** 口令只保护本地长期身份私钥；流量密钥由每次连接的新临时密钥协商派生，职责不同。
7. **文件如何避免一次全部读入内存？** 按 64 KiB 分块传输并增量更新 SM3，接收端先写临时文件，完成大小和摘要验证后再发布为完整文件。
8. **TCP 为什么需要长度前缀？** TCP 提供字节流，不保留消息边界。先读固定长度的帧头，再循环读取指定长度内容，并限制帧大小。
9. **第三方密码库为什么还需要适配？** 项目补充了 gmssl 3.2.2 的随机源、公钥前导坐标、曲线点和 SM2 C3 校验边界；应能定位代码并说明依赖版本，而不是声称自行实现密码算法。
10. **还有哪些不足？** 自定义协议未独立审计；仅支持单对端；没有实时音视频、群聊、中继、自动公网穿透和断点续传；其他平台与大文件上限尚未完整验证。

## 展示前的操作顺序

1. 按 README 安装依赖，运行 16 项自动测试，确认当前环境可用。
2. 启动双窗口演示，交叉核对完整指纹，建立安全连接。
3. 双向发送文字，传输 `samples/` 中的图片和短视频，展示图片预览与 SM3 校验。
4. 打开“会话与身份”和“安全实验”，说明各算法职责并演示篡改、重放拒绝。
5. 对照自己的负责模块讲解代码，主动说明教学协议和实测数据的适用范围。
