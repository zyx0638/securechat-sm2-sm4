# 中级实验验收演示与问答

## 五分钟演示顺序

1. 双击 `start_demo.bat`，解锁双方身份。说明 Alice 和 Bob 是两个独立通信端。
2. 首次连接时核对两端完整 SM3 身份指纹并分别确认。后续连接可在“查看信任记录”展示已保存身份。
3. Alice 发送中文文字，Bob 回复，证明双方均能发送和接收。
4. 发送 `samples/sample-image.png`，查看接收端预览与两端相同的 SM3 摘要。
5. 发送 `samples/sample-video.mp4`，打开接收目录播放，说明视频内容以分块密文传输。
6. “会话与身份”展示 SM2、SM3、SM4、X25519 的对应用途；“安全实验”日志展示 SM2 加密挑战验证及密文记录。
7. 运行篡改与重放实验，展示两项“已拒绝”。它使用独立临时会话，不修改真实聊天通道。
8. 断开后重新监听、连接，观察新会话标识，说明临时密钥每次重新生成。运行自动测试展示异常路径。

## 原理问答

### 为什么不直接用 SM2 加密整个视频

SM2 是非对称算法，计算代价高，适合身份认证和少量数据。本实验使用 SM2 签名绑定握手，并加密 32 字节随机挑战；实际文字、图片和视频使用高效的 SM4 对称加密。

### SM2 签名和 SM2 加密分别在哪里

`Identity.sign/verify` 对握手签名和验签；`Identity.encrypt/decrypt` 加解密随机挑战。`Peer._serve` 在派生会话密钥、确认对端指纹后进行双向挑战，正确回显后才进入可通信状态。

### X25519 为什么能让双方得到同一个秘密

双方独立生成临时私钥和对应公钥，只交换公钥。X25519 用自己的私钥与对方公钥计算共享秘密，两端结果相同。公钥由 SM2 签名，阻止未持有对应身份私钥的第三方替换协商参数。HKDF-SM3 将共享秘密和完整握手摘要组合，派生用途独立的密钥。

### 公钥从网络收到就可以相信吗

不可以。签名只能证明某人持有相应私钥，不能自行证明那个人就是希望联系的同学。首次连接要通过现场或其他可信渠道核对完整身份指纹。保存信任记录后，同名对端的公钥改变会被拒绝。未经可信渠道核验的首次点击不能防止中间人攻击。

### SM3 摘要相同就能证明没人篡改吗

普通摘要可以同时被攻击者替换，不能单独提供来源认证。本实验每个传输记录先验证带秘密认证密钥的 HMAC-SM3；文件末尾的 SM3 摘要也在经过认证的加密记录中传送。摘要用于整文件一致性检查，HMAC 用于阻止攻击者伪造记录。

### 为什么必须先验 MAC 再解密

本实验采用 Encrypt-then-MAC。认证码覆盖会话标识、序号、IV 和密文，验证成功后才执行解密和去填充。被修改的密文在解密前被拒绝，避免向未认证输入暴露填充处理差异。

### 怎么防重放

每个方向维护独立且严格连续的 64 位序号，并把序号放入认证范围。已经接收的序号不能再次使用，乱序记录也被拒绝。会话密钥绑定完整握手及随机数，旧会话记录不能拿到新会话继续使用。

### 为什么要派生多个密钥

HKDF-SM3 输出 96 字节，每个方向各用 16 字节 SM4 密钥和 32 字节 HMAC 密钥。加密和认证用途分离，两个方向也分离，避免反射和跨用途混用。

### 密钥保存在哪里

长期 SM2 私钥在 `runtime/<身份>/identity.json`，使用 scrypt 从用户口令派生保护密钥，再用 AES-GCM 加密保存；公钥和盐不是秘密。临时 X25519 私钥及会话密钥只在进程内使用，断开后释放引用。Python 不保证内存物理清零，不能声称彻底擦除。密码遗失不能解开旧身份文件。

### 文件很大时会不会一次读进内存

文件按 64 KiB 读取、加密和传输，摘要同步增量更新。接收端写临时文件，结束时检查大小和 SM3，通过后才改名发布。单端同一时间只发送一个文件；双方可以各自发送，文字也能在块之间交错。

### TCP 已经可靠，为什么还需要长度前缀

TCP 是有序字节流，不保留应用消息边界。一次发送可能多次接收，多次发送也可能一起到达。本实验使用四字节大端长度前缀和循环读取，限制最大帧大小，再交给认证解密层。

### 如何验证实际效果

使用不同中文消息、PNG 图片、真实 MP4、空文件和较大二进制文件；比较接收文件原始字节；运行测试检查修改密文、重复序号、跨会话记录、错误口令、错误文件摘要及中断清理。截图和输出放在 `output/evidence/`。已有测试不是对所有安全性质的形式化证明。

### 是否全部采用国密算法

不是。核心加密、身份签名和摘要优先采用 SM2、SM3、SM4；临时协商使用 X25519，私钥容器使用 AES-GCM。这满足优先采用国产算法的方案设计，但不能称为国密 TLS、全套国密或已经过商用密码认证。

## 关键代码定位

| 位置 | 重点 |
| --- | --- |
| `crypto.py` 的 `Identity` | OS 安全随机数、SM2 签名与公钥加密、C3 校验、加密私钥文件 |
| `crypto.py` 的 `Handshake.finish` | 签名验证、握手绑定、X25519 与 HKDF-SM3 |
| `crypto.py` 的 `Channel.open` | HMAC 比较、序号检查、先认证后解密 |
| `protocol.py` 的 `Peer._serve` | 身份指纹、SM2 挑战、双向密钥确认 |
| `protocol.py` 的 `send_file` 和 `_file_end` | 分块、流式摘要、完成回执和不覆盖同名文件 |
| `gui.py` 的 `ask_trust` 和 `poll` | 工作线程与界面主线程之间的事件队列 |
